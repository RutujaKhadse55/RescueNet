# RescueNet Threat Model & Security Architecture

## 1. Overview & Security Philosophy

RescueNet is designed for life-and-death disaster scenarios where cellular networks, power, and official communications are compromised. In such environments, adversarial conditions can arise from panic, malicious actors seeking to divert emergency resources, looters exploiting evacuated zones, or adversaries attempting denial-of-service on the mesh.

The security architecture rests on three tenets:

1. **Never silently drop an SOS**: A false negative (ignoring a real victim) can be fatal. Suspicious or unverified reports are flagged with low-trust warnings, never purged.
2. **Cryptographic Integrity & Attribution**: Every packet is signed at the edge using Ed25519; authenticity is verifiable offline without central certificate lookups.
3. **Privacy by Default**: Ephemeral rotating identifiers prevent passive tracking of survivors while maintaining cryptographic accountability.

## 2. Threat Analysis Matrix

| **1** | **Spoofed SOS**               | Malicious actor generating fake emergency alarms to divert NDRF/SDRF assets away from real disasters.                                      | Emergency dispatch accuracy, rescuer personnel and vehicle bandwidth.   | - Every SOS is cryptographically signed by an on-device Ed25519 private key generated in Android Keystore / Keychain.<br>- Node trust-scoring engine integrates physical sensor corroboration (barometric delta, accelerometer motion, GPS accuracy bounds).<br>- Multi-witness validation: clusters with multiple independent peer nodes receive higher confidence scores. | Attacker with a physical cluster of sybil phones in a vehicle can still craft multiple signed keys. | **2** | **Replay Attack**             | Malicious node capturing an old SOS beacon from a resolved disaster and re-broadcasting it days or weeks later.                            | Network capacity, rescuer situational awareness.                        | - Strict packet header timestamp ($T_{\text{origin}}$) with monotonic clock and bounded expiration window ($\Delta t \le 6\text{ hours}$).<br>- Packet ID is BLAKE2b hash over `(SenderPubKey + MonotonicSeqNo + Timestamp + Payload)`.<br>- Sliding-window Bloom filter + LRU cache on all relay nodes drops already-processed `packet_id`s.                               | Nodes with severely drifted system clocks (> 1 hour skew) might reject valid packets or accept expired ones. Mitigated by relative mesh clock synchronization protocols.                          |
| **3** | **Flooding / Mesh DoS**       | Rogue node broadcasting high-frequency bogus packets to congest the 2.4 GHz ISM band and drain survivor phone batteries.                   | Mesh radio bandwidth, survivor battery longevity, channel airtime.      | - Rate limiting at the BLE GATT and advertising ingress layer (max $N$ packets/minute per peer MAC/pubkey).<br>- Strict Priority Queue: SOS packets bypass queue; text messages and location shares are aggressively dropped under congestion.<br>- Battery-aware duty-cycling: nodes enter defensive backoff if radio duty cycle exceeds safety threshold.                 | An attacker executing high-power RF jamming on BLE frequencies (2.4 GHz) can drown out physical signals. Physical RF jamming cannot be prevented by software; requires SMS or satellite fallback. |
| **4** | **Malicious Relay Tampering** | Byzantine or compromised intermediate node modifying survivor coordinates or triage data in transit.                                       | SOS payload integrity (GPS coordinates, casualty counts, triage score). | - End-to-end cryptographic signature (Ed25519) calculated over immutable payload fields.<br>- Relaying nodes only append relay metadata (hop count, RSSI, relay pubkey) in an unsigned outer wrapper or verifiable onion record.<br>- Signature verification failure on any node flags the packet as corrupted and discards the relay step.                                 | An attacker can refuse to forward packets (black-hole attack). Multi-path random walk and epidemical gossip flooding overcome single-node dropouts.                                               |
| **5** | **Location Privacy Leakage**  | Stalkers, looters, or hostile actors scanning BLE packets to track individuals or locate vulnerable, abandoned structures.                 | Survivor physical location, identity, and personal distress details.    | - Rotating Pseudonymous Node IDs: Public keys and BLE MAC addresses rotate periodically or upon major relocation.<br>- Direct peer chat messages are end-to-end encrypted using X25519 ECDH + XChaCha20-Poly1305.<br>- Broad SOS alerts broadcast approximate spatial grid or require explicit survivor opt-in for precise meter-level coordinate disclosure.               | In a public SOS broadcast, coarse GPS must be readable by any listening rescuer (and therefore nearby eavesdroppers). Survivors are informed that emergency SOS is a public safety beacon.        |
| **6** | **Rogue Rescuer Credentials** | Impersonator crafting fake `RESCUER_ACK` packets telling trapped victims "help is arriving, stay put" to induce complacency or cause harm. | Rescuer authority, survivor trust and tactical decisions.               | - Rescuer mode requires an X.509/Ed25519 authorization certificate signed by the National/State Disaster Agency CA (`AGENCY_CA_PUBLIC_KEY`).<br>- Certificates are embedded offline in the application and verified locally on survivor phones.<br>- Only signed agency ACKs render as verified green status badges in survivor UI.                                         | Compromise of an agency CA root key. Mitigated by short validity windows (e.g., 30-day incident certs) and offline certificate revocation lists (CRL) distributed over mesh.                      |
| **7** | **SMS Spoofing / Tampering**  | Attacker sending forged SMS messages to the emergency inbound virtual number claiming false emergencies.                                   | SMS Ingestion Gateway, PostGIS triage database.                         | - SMS payload is an ASCII-armored Base64 representation of the exact same signed binary packet schema used over BLE.<br>- The backend verifies the Ed25519 signature before inserting into the PostGIS database.<br>- Inbound SMS webhook verifies provider HMAC signature (`SMS_WEBHOOK_SECRET`).                                                                          | Telco-level SMS spoofing of Caller ID does not compromise the cryptographic signature inside the SMS body.                                                                                        |
| **8** | **Stolen / Captured Device**  | Looters finding abandoned or lost phones with RescueNet running to extract sensitive data or hijack identity.                              | Local SQLite database, cached mesh messages, survivor identities.       | - Local database encrypted at rest using SQLCipher with keys stored in hardware-backed Keystore/Keyring.<br>- Ephemeral message lifetimes: text chats automatically purged after incident resolution or retention threshold (`RETENTION_DAYS`).<br>- Remote and manual wipe trigger in application settings.                                                                | Physical device seizure with unlocked screen while app is open. Survivor identity is pseudonymous, minimizing stored PII.                                                                         |
